Consequence: claim/evidence traceability is complete inside the artifact, and the `claims`/`claim_evidence` rows arrive with the script stage (each script sentence then references the package claims it came from). Ratify, or approve (a) nullable `script_id` on `claims` — a table rebuild, approval-gated like OD-10 — or (b) a new `research_claims` table. |
| OD-16 | 🟡 | **The script document schema does not encode the section structure.** `ScriptDocSchema.sections` is `.min(1)`, not `.min(4)`: the gate can legitimately drop a whole section (a hook whose only sentence broke a quotation rule), and a schema violation there would make the artifact *unparseable* — the one state an operator cannot review or repair. The structure rule therefore lives in the engine's lint (`missing_section`, hard) and in `quality.reviewRequired`, so a damaged script is stored, readable and flagged. Ratify, or require the schema to reject under-structured documents and have the stage fail instead of storing them. |
| OD-17 | 🟡 | **The gate deletes offending narration instead of rewriting it.** When a corrective round leaves a hard violation (an unsupported fact, an invented quotation, a fabricated source), the sentence is removed rather than auto-rewritten, its claims leave the ledger, and the script is marked `reviewRequired` with the removed lines verbatim in `quality.droppedSentences`. Rationale: a model that already produced the violation is not the safest thing to trust with the repair, and a dropped line is recoverable while a plausible-looking fabricated fact is not. Consequence: an episode can lose a whole section this way (see OD-16). Ratify, or ask for an AI repair step that may rewrite offending sentences (bounded, still gated). |
| OD-18 | 🟡 | **`claims.score` carries the research confidence.** The script stage writes the ledger's confidence (0–1) into `claims.score` and `claim_evidence.score`; there is no separate "script confidence". Ratify, or split the two in a later migration (needs the OD-10 table-rebuild approval). Provisional reading: the number describes the claim's evidence, and the script stage has no evidence of its own to score. |
| OD-9  | 🟡 | **Persistence implementation deviates from AD-04's wording**: AD-04 named *Drizzle ORM*; Phase 2 implements plain SQL DDL + a hand-written migration runner + zod validation on `node:sqlite`. Rationale: zero native deps, full control of the drift guard, no codegen step, and the SQL stays Postgres-portable. Ratify (amend AD-04) or ask for Drizzle — porting is confined to `packages/db`. |

| OD-19 | 🟡 | **No `scenes` rows are written; the manifest is a CAS artifact.** The `scenes` table's `kind` CHECK constraint allows only `title \| talk \| fact \| media \| quote`, and widening a CHECK needs a table rebuild — which the safety rules forbid without approval (OD-10). The six scene types map onto those five (`CHARACTER`/`HYBRID` → `talk`, `EVIDENCE` → `quote`, `DIAGRAM` → `fact`, `ENVIRONMENT` → `media`, `TRANSITION` → `title`) via `legacySceneKind()`, and the artifact carries everything the rows would (`kind: scene_graph`, role `scene_manifest`). Ratify, or approve the one-time rebuild so the `scenes` table can hold the six types (and the richer `scene_graph` document as its `data`). |
| OD-20 | 🟡 | **Scene planning is entirely deterministic — no AI step.** Shot choice, camera variation, animation grammar, text/diagram content and the asset list are rules over the script's own visual cues; the only "content" the planner emits is verbatim (a claim's statement, a quoted span, the spoken line). Rationale: the script already decided what each sentence shows, and a model in this loop would make one script produce a different video twice (AD-07) at nonzero cost. Ratify, or ask for an AI scene-design step (a model choosing shots/framing/visual ideas from the script) — it would be a separate, opt-in pass with its own prompt, budget and schema. |
| OD-21 | 🟡 | **A manifest may carry narration it cannot trace to sentence ids.** `narration.kind` is `sentence` (the planner's output, sentence-addressable), `paragraph` (script narration a legacy v1 artifact or a hand-written plan cannot address), or `transition` (a section's spoken bridge). A `paragraph` scene is checked by containment in the script's narration rather than by sentence, so a hand-written plan is possible without faking ids. Ratify, or require sentence-level traceability always (which makes a v1 script artifact unplannable). |
| OD-22 | 🟡 | **A character library is a directory of documents, not database rows.** `characters/index.json` names the definitions, `characters/<id>.json` holds them, `assets/<id>/*.svg` are the layers — all versioned in the repo with a content hash per asset, and a set-wide hash in `CharacterLibrary.hash`. Rationale: a character is reviewed art plus numbers, it benefits from diffing and code review, and the CAS/hash discipline already covers integrity; a DB-backed library would need asset upload plumbing for no gain in this phase. Ratify, or move definitions into the database (the `CharacterLibrary.from(documents)` constructor is the seam: same contract, different source). |
| OD-23 | 🟡 | **The layer model is paint-region replacement, not a rig.** A `pose` owns the figure (`body` + `arms`), a `gesture` may replace those arms and add a `prop`, `clothing` covers `torso`, an `expression` redraws `face`, an `accessory` goes over `worn`. Resolution is deterministic, needs no skeleton, and a definition cannot produce a physically impossible stack (exactly one layer per region). The trade-off: a new pose *is* a new drawing rather than a joint rotation, and there is no interpolation between variants (GAP-24). Ratify, or adopt a rigged model (SVG joints / Rive / Lottie) — that changes what an asset is, so it is a decision, not an implementation detail. |

## Implementation gaps (deliberate, phase-appropriate)

| ID    | Status | Description |
|-------|--------|-------------|
| GAP-1 | 🟡 | No HTTP/API surface for the new tables yet (routes arrive in the phase that consumes them). Phase 2 is library + tests only. |
| GAP-2 | 🟢 | Job executor: **implemented in Phase 3** (`packages/jobs` — claim loop, stage runner, retries, gates, reuse; see `docs/architecture/job-orchestration.md`). Remaining: wiring it into `apps/nexus` with real tasks and DB/CAS paths (tracked as GAP-9). |
| GAP-3 | 🟢 | Episode transitions are now **enforced** by `packages/jobs/src/machines.ts` (`assertEpisodeTransition`, separate long/short tables) and applied only through the runner; `Repo.setEpisodeState` deliberately stays permissive so operators/repairs are not blocked by machine rules — legality is a pipeline-layer concern, as planned. A test asserts the stage graph and the episode machine cannot drift apart. |
| GAP-4 | 🟡 | `media_assets` supports `image`/`video`/`document` kinds. Phase 4 added the `MediaProvider` interface with a deterministic fake and a tested SSRF guard, but **no real acquisition adapter** — rows are still only insertable by the operator/API. Real adapters await the licence policy decision (OD-8) and the search provider (OD-5). |
| GAP-5 | 🟠 | No backup/DR wiring (Litestream → object storage) — AD-04 consequence, scheduled for the deployment phase (OD-4). Until then, backup = copy the DB file + the CAS directory together. |
| GAP-6 | 🟡 | ~~`provider_call_log` records usage but nothing enforces the quota yet.~~ **Phase 4 delivered the decision half**: `BudgetGuard` reads the accounts/log, fails closed at the cap, degrades a live adapter to `manual` at 90% and applies cooldowns; `invoke()` refuses, degrades or proceeds accordingly. Phase 3 gave tasks a parking mechanism (`{ waiting: "QUOTA" }` → job `WAITING_GATE`), so a task can already stop cleanly instead of failing; the budget guard that *decides* to park is wired when real providers are (AD-13). |
| GAP-7 | 🟡 | CAS garbage collection does not exist. Blobs are only added, never pruned. `CasStore.list()` was added in Phase 3 specifically so a reconciler can diff stored blobs against the `artifacts` table; the reconciler itself is not written. |
| GAP-8 | 🟡 | `job_logs` has no retention/compaction policy. Long-lived installations will accumulate rows; a pruning job (or a `logs_keep_days` setting) is needed before production. |
| GAP-9 | 🟡 | The app/worker entrypoints are **not yet wired** to the new orchestrator: `apps/nexus/src/worker.ts` still runs the Phase 1 heartbeat stub. Wiring is deliberately deferred to the phase that provides real tasks (a worker with zero registered tasks can only idle), together with `NEXUS_DB_PATH`/`NEXUS_CAS_DIR` config, the `--dry-run` CLI flag (the provider-side helper exists: `dryRunConfig`) and the job HTTP routes. |
| GAP-11 | 🟠 | **Media SSRF guard validates the URL, not the resolved address.** `assertPublicHttpUrl` refuses non-HTTP(S), credentialed URLs, localhost/`.local`, private/CGNAT/link-local/loopback IPv4 and IPv6 (including IPv4-mapped forms, after a real bypass was found and fixed) — but a *public* hostname that resolves to a private IP (DNS rebinding / internal resolver) is still reachable. Mitigation when a real media adapter lands: resolve first and pin the address (or run fetches through a proxy with an egress policy). No real fetcher exists yet, so nothing is exposed today. |
| GAP-12 | 🟡 | **Storage `list()` reads a directory, not the DB.** `LocalStorageProvider.list()` / `CasStore.list()` enumerate blobs on disk, which over-reports blobs that no `artifacts` row references (and cannot see rows whose bytes are gone). The reconciler that diffs the two is GAP-7; until then, treat `list()` as "bytes present", not "artifacts known". |
| GAP-13 | 🟡 | **Provider cache has no eviction.** `<dataDir>/cache/providers` grows with every distinct prompt/query; entries are content-addressed JSON and cheap, but an LRU/TTL sweep (or a `cache_keep_days` setting) is needed before a long-running deployment. Caught by: nothing yet — flagged proactively with the CAS GC work (GAP-7). |
| GAP-14 | 🟡 | **Metering is opt-in per adapter.** Adapters with no `provider_accounts` row are allowed without limits (deliberate: a local fake has no quota). A real provider therefore needs its account row seeded before its free tier is protected; the dashboard/CLI path that seeds accounts is not written yet. |
| GAP-15 | 🟠 | **Evidence is snippet-only.** There is no page-content fetch + HTML-extraction capability yet, so a source's quotable text is whatever the search provider returned (or what an operator pasted). The package records this per source (`retrieval: provider_snippet \| operator_text \| unavailable`), and a source with no text contributes no evidence — but the verification depth is limited by snippet length. Mitigation planned: a `fetch(url) → text` capability (behind the same provider interface, with the SSRF guard), added when a real research adapter lands. |
| GAP-16 | 🟡 | **The verification gate is reported, not enforced.** `verification.reviewRequired` / `blockingClaimIds` are computed and logged, but the `fact_check` stage that parks a job at `FACT_REVIEW` is not built (Phase 6+), and no HTTP surface exposes a package for review (GAP-1). Also: no *real* research adapter yet (`none`/`fake`/`manual` only), and no semantic re-check of a finished script's claims against the package. |
| GAP-17 | 🟡 | **Visual cues are descriptive only.** Each sentence may carry `visual {kind, description, searchHint}`, and the script engine guarantees the shape and the defaults — nothing resolves a cue to an asset, executes a search hint, checks a licence or assigns timing. The media/scene stages own that (plan-Phase 1), and no rendering exists in this phase by instruction. |
| GAP-18 | 🟡 | **No `fact_check` stage task.** The stage exists in the versioned stage graph (`FACT_CHECKING` → `SCRIPTING`) and the script task prefers its `output.packageHash` when present, but no task is registered for it, so a job whose step list includes `fact_check` fails with `ConfigurationError` (fail-fast, not silence). The script stage therefore reads the research package directly, and `params.researchPackageHash` exists for operator-supplied packages. |
| GAP-19 | 🟠 | **No semantic check that the narration matches the claim it cites.** A `fact` sentence is validated to cite a cleared claim and to be structurally sound, but the wording is not compared with the claim statement beyond quotation checks — a paraphrase that drifts (right citation, wrong emphasis) would pass. Mitigation planned with the editor/approval surface (GAP-1) or a future NLI-style checker behind the provider interface; flagged now so it is a known limit rather than an assumed guarantee. |
| GAP-10 | 🟢 | No duplicate-execution protection was needed at the DB level beyond the fingerprint checks and lease claiming; a partial unique index on `(input_hash, step_key)` for DONE steps was *considered and rejected* — legitimate re-runs (invalidation → re-execute → new checkpoint) and multi-job reuse both need more than one row per fingerprint, so uniqueness would break repairability. |

| GAP-20 | 🟡 | **Nothing consumes the manifest yet.** The `plan` stage stores a `scene_graph` artifact, and no media, voice, caption or render task reads it: assets stay `status: "planned"` with an empty `uri`, and `camera`/`animation`/`transition` are data with no executor. The next stages (`source_media`, `voice`) own that; this phase deliberately stops at the contract. |
| GAP-21 | 🟡 | **Diagrams carry no plotted data.** `diagram.series[]` is always empty because a research claim is a statement, not a table: `number_highlight`/`bar_chart`/`line_chart`/`table` scenes cite their claims and carry verbatim annotations, but nothing extracts a number series. A data-extraction step (deterministic over stored source text, or an AI pass behind the provider interface) is needed before a chart can be drawn. Related: the figures shown are the claim's wording, so a unit or scale must come from the claim too. |
| GAP-22 | 🟠 | **No licence enforcement at planning time.** Every planned asset defaults to `licence: "unknown"`; the manifest does not consult `projects.config.allowedLicenses` (AD-09) because nothing has been sourced yet. The media stage must refuse assets whose licence is not allowed; until it exists, a plan is a *request*, not a rights clearance. |
| GAP-23 | 🟠 | **Text and narration are not cross-checked semantically.** A claim card shows the claim's own wording and the sentence beside it cites the same claim, but nothing verifies the sentence paraphrases it faithfully (the same limit as GAP-19, one stage later). Also: `estimatedDurationSec` is words ÷ 2.5 words-per-second until the voice stage returns real timings, so every planned duration is an estimate by construction. |
| GAP-24 | 🟡 | **No rig and no animation between variants.** A `state` picks a pose/expression/gesture variant; nothing tweens one into another, walks a cycle, blinks or lipsyncs, and nothing draws: the resolver hands out an ordered layer stack plus placement, and the renderer (Phase 1 of the plan) does not exist yet. A character therefore reads as a posed figure, not a moving one. |
| GAP-25 | 🟡 | **The demonstration set is flat, hand-generated SVG — no raster or generated art.** `kind` is `"svg"` only, there is no image-model integration and no artist pipeline; the set exists to exercise the system (identity, palette, poses, expressions, gestures, clothing, accessories, asset hashes). A production set needs either drawn art or a generated-art pipeline that produces layers *with* the slot/paint/region contract — and a decision about whether generated character art is allowed at all (OD-8). |
| GAP-26 | 🟡 | **A scene cannot override a performance.** A manifest says `{characterId, state}`; the state maps to pose/expression/gesture by the documented table, and the rest comes from the definition's `defaultPerformance`. Hand-writing a different look for one scene means editing the definition (or pre-resolving with `library.resolve` and rendering from that). Adding per-scene overrides means extending the phase 7 schema, which is a contract change; it also needs a story for what a renderer does when a definition lacks an overridden id. |
